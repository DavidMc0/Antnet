# Antnet Gateway against WebRTC: measurements, 19 November 2026

These are for DEMO.md 12.14 step 2. The raw data is in `2026-11-19-gateway-vs-webrtc.jsonl`, one line per open. The script that made it is `tools/measure-gateway.mjs`.

## Set-up

- **Machine:** one Windows 11 PC on a home connection, mainnet, 14:58–15:30 UK time.
- **Browser:** headless Chromium (Playwright 1.65). Every open used a new browser context, so the browser held nothing from earlier opens.
- **Gateway path:** the local loader (`npm run build:local`) on `*.antnet.localhost:47114`, served by antnet-gateway 0.1.0 and reading through antd 0.17.0.
  - antd ran with `--chunk-cache-capacity 1`, so it couldn't keep any site's chunks in memory.
  - antd had restarted a few minutes earlier and had about 134 peers.
- **WebRTC path:** the hosted loader at `*.antnet.autonomirror.com`, with SDK 0.1.5 in the browser.
- **Runs:** ten per site and path. The paths alternated, so both saw the same network conditions.
- **Times:**
  - The **open** time runs from starting the page load until the loader had installed the site.
  - The **download** time is the loader's own record of fetching the archive.

**All 100 opens succeeded.** Every gateway open was fetched through the gateway, and every hosted open over WebRTC.

## The first fetch of each site through antd

This is the only truly cold gateway fetch: antd hadn't seen the site before. The WebRTC download is from the same few minutes.

| Site | Archive | Gateway download | WebRTC download |
| --- | --- | --- | --- |
| Start | 157 KiB | 17.0 s | 13.7 s |
| Library | 1.0 MiB | 12.2 s | 6.5 s |
| Cinema | 6.0 MiB | 13.6 s | 10.1 s |
| ColonySim | 91 KiB | 18.3 s | 10.2 s |
| Download Button | 6.0 MiB | 31.4 s | 36.9 s |

Start and Library were fetched in a trial run just before the main run, so those two rows come from the trial.

**On a first fetch, the gateway was no faster than the browser,** and usually slower. Five fetches are too few to say by how much.

## Later fetches of the same site

These are runs 2–10. antd's chunk cache held at most one chunk, yet the native client fetched each site it had fetched before in about a second or two. The cause isn't known from here: perhaps the client keeps its connections to the nodes that hold those chunks, or remembers where they are.

| Site | Gateway open, median (range) | WebRTC open, median (range) | Gateway download, median | WebRTC download, median |
| --- | --- | --- | --- | --- |
| Start (pointer) | 3.8 s (2.6–5.0) | 31.5 s (26.4–51.5) | 1.8 s | 14.0 s |
| Library | 1.1 s (0.7–1.9) | 8.6 s (8.0–8.9) | 0.8 s | 6.4 s |
| Cinema | 1.5 s (0.9–1.9) | 12.3 s (10.4–16.8) | 1.3 s | 10.3 s |
| ColonySim | 2.3 s (1.6–4.3) | 12.4 s (11.6–13.6) | 2.1 s | 10.2 s |
| Download Button | 4.0 s (3.0–6.7) | 18.3 s (10.3–38.9) | 3.7 s | 16.1 s |

**This isn't a like-for-like comparison.** Every WebRTC open started a new client in a new context. The gateway's client had been running all along and had fetched these sites before. In normal use, a browser that already has a site installed opens it from its own storage on either path, with no fetch at all. So this advantage shows only where the browser has nothing installed but the gateway has fetched the site before: another browser, a cleared one, or a second person on the same computer.

## Resolving a pointer

Start is a pointer site, so every open resolves its pointer to find the latest version. That is never served from a cache.

- **Gateway:** median 1.3 s (0.9–3.2 s) over ten opens.
- **WebRTC:** median 14.4 s (12.6–21.8 s).
- The very first gateway resolve, in the trial run, took at most about 7 s.

The pointer resolve accounts for about half of Start's WebRTC open time. It is also the work behind every background update check.

## Records the browser can't reach

The prepared 4K 30 fps copy of the Cinema film, `289d3381…5a51` (149 data records, 608 MB), had records the browser couldn't fetch on 17 November (PROGRESS.md, "Cinema in 4K"). Each was tested by reading one byte from the middle of the record. The two tests ran minutes apart.

| Record | Through the gateway (antd) | Through the browser SDK, today |
| --- | --- | --- |
| 11 | arrived in 33.1 s | failed after 129.0 s: "Missing chunk `2184f7b0…9621`" |
| 70 | arrived in 9.5 s | failed after 94.6 s: "Missing chunk `219bce56…3a24`" |
| 100 | arrived in 23.0 s | arrived in 12.8 s (it failed on 17 November) |

**Two records the browser still can't fetch arrived through the gateway.** This is the claim the measurements support most firmly.

## What can be said

- **Supported:**
  - The gateway reached records the browser can't (two of two).
  - It resolved pointers about ten times faster.
  - It re-fetched sites it had fetched before in 1–4 s, against 9–31 s for a fresh browser.
- **Not supported:** that the gateway is faster on a cold first fetch. In these runs it wasn't.
- **Limits:** one machine, one network and one half-hour; headless Chromium only; antd 0.17.0 with its chunk cache at one chunk.
- **Worth repeating later:**
  - More cold first fetches: restart antd between them, or use sites it has never seen.
  - Whether the fast re-fetches survive an antd restart.
